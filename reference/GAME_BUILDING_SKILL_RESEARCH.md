# 游戏构建 Skill 调研：让 AI 生成的游戏可调控、可持续迭代

调研日期：2026-10-31。目标是为后续的游戏开发 skill 定义工作方法，不在本次创建或修改 skill，也不改动游戏源码。

## 结论

核心应是“先建立可调的游戏规则，再按小步扩展”，而不是要求 AI 一次生成更大的游戏。Skill 需要同时约束两层：

- **游戏可调控**：设计者能在 Inspector、关卡数据或调试面板上改植物、敌人、波次、经济和节奏；无需为了常规平衡调整去改代码。
- **AI 可控、项目可长期发展**：AI 每次只改清楚界定的一块，遵守稳定的系统边界、内容 ID、验证入口和项目记录；避免不断叠加在单体脚本里的临时功能。

对于当前 Unity 2022.3 的 PVZ 前院原型，推荐保留已能玩的场景，优先把游戏平衡参数和波次外置为 `ScriptableObject` 配置，再逐步拆解职责。此阶段不需要 ECS、通用插件框架、在线配置服务或大型事件总线。

## 调研依据

- Unity 2022.3 的 [ScriptableObject 文档](https://docs.unity3d.com/2022.3/Documentation/Manual/class-ScriptableObject.html)将其定义为可独立于脚本实例保存的数据容器，适合将共享的植物、僵尸、关卡等定义从行为代码中分离。
- Robert Nystrom 的 [Game Programming Patterns](https://gameprogrammingpatterns.com/)提供了状态、组件、事件队列、数据局部性等模式。适合按实际变化点择用，不应把模式当作必须实现的清单。
- 本地 [PVZ 源码调研](SOURCE_RESEARCH.md)显示，候选项目中已有按 JSON 波次配置驱动关卡、植物/僵尸分系统，以及项目数据和行为分开的例子；同时也记录了许可证、依赖和完成度限制。它们适合作为结构参考，不能默认整套搬入当前项目。
- 当前原型的主要玩法和 UI 集中在 `Prototype/Assets/PVZPrototype/PrototypeGame.cs`；植物成本、冷却、行列、刷怪数量及节奏在代码常量/流程中。`Prototype/README.md`列出了当前玩法与运行方式，`ASSET_SOURCES.json`已维护素材来源。这意味着目前最直接的维护收益来自配置外置和职责收敛，而非换引擎或重做场景。

## 目标工程结构

建议 Skill 按下面边界组织游戏。规模小时允许暂留少量代码；只有职责确实变化或冲突时才拆文件。

| 边界 | 放什么 | 对 PVZ 原型的例子 |
|---|---|---|
| 配置数据 | 设计者常调的数值与内容定义 | 植物花费、冷却、生命、伤害；僵尸速度、生命；阳光产量；关卡初始资源 |
| 运行规则 | 使用配置驱动模拟，不持有内容制作流程 | 种植校验、目标检测、伤害、产阳光、胜负判断 |
| 关卡编排 | 可读、可复现的内容时间表 | 波次时间、行、敌人类型与数量、波间条件 |
| 表现与输入 | 只把游戏状态呈现出来并转为意图 | 动画、UI、鼠标种植、暂停按钮、音效 |
| 调试工具 | 只在开发模式下提供调试操作和观察信息 | 暂停/单步、倍速、跳波、指定行刷怪、资源调整、显示碰撞/网格 |
| 项目记录 | 给未来开发者与 AI 的维护入口 | README、系统边界、配置说明、改动记录、存档格式版本（需要存档时） |

Unity 实施建议：可编辑定义使用 `ScriptableObject` 资源；运行时数据如当前血量、计时器、位置则放在每局状态中，不写回共享定义资源。波次用明确的数据结构或关卡资产表达，先不引入外部 JSON 加载器。设计者能否调控，应以“改一个关卡内容不需要改运行时代码”为检验标准。

## Skill 应规定的工作流

1. **先读再改**：读取 `AGENTS.md`、README、场景入口、相关脚本、资源配置和 Git 状态；确认 Unity 版本、当前可玩流程、已知限制。
2. **把需求写成可观察结果**：明确玩家能做什么、怎样算完成、哪些现有行为不能破坏。未给出范围时，先做最小垂直切片。
3. **指定变更边界**：列出要改的系统和数据文件。内容调整优先改数据；规则变化只改对应规则；避免无关格式化与整场景重生成。
4. **先定义配置再接入逻辑**：写出字段、默认值、校验规则、引用关系和缺省表现，再迁移现有硬编码。每项配置应有明确单位、范围和 Inspector 提示。
5. **保持兼容和可恢复**：内容使用稳定 ID，不用数组顺序作为永久身份；存档加入后为 schema 加版本并提供迁移；生成型场景/素材要保留来源与重建说明。
6. **做可重复的最小验证**：对配置加编辑器校验，对核心规则加 EditMode/PlayMode 测试；验证最小游戏循环与边界条件。仅在用户要求时执行会打包、覆盖最终制品或发布的操作。
7. **更新维护记录**：说明改了什么、如何调参、运行入口、验证结果和未覆盖部分；新增系统时同步更新 README/开发说明。

## 当前项目的推荐演进顺序

1. **先建立基线**：记录 Unity 版本、场景入口、按键、已有玩法和验证方法；清理/确认 Git 基线后再改。当前仓库显示无提交，第一次系统性改造前应先建立可回退版本。
2. **参数外置**：建植物、僵尸、关卡/波次定义资产，先迁移成本、冷却、生命/伤害、刷怪时间与数量。增加编辑器校验，防止缺资源、非法行列、负数和重复 ID。
3. **拆解热点职责**：把原型主脚本里最常独立变化的“关卡流程、经济/冷却、战斗更新、输入/UI”逐步分离；每一步保持旧场景可玩，不一次全量重写。
4. **补开发调试面板**：加入刷波/刷敌、改倍速、暂停、清场、显示数值和重置。调试工具需有开发模式门槛，避免进入正式玩家流程。
5. **需要内容规模时再升级**：关卡数量增长后再考虑表格/JSON 导入导出、内容校验命令或关卡编辑器；出现存档、Mod 或热更新需求后，再设计 ID、兼容策略和版本迁移。

## AI 修改的质量门槛

- 每次任务要能说明一个主要结果，并有可复现的验收步骤；拒绝“顺手重构全项目”。
- AI 不得擅自改变核心数值、存档格式、输入映射、素材来源或场景生成入口；需要调整时必须在变更说明中列出。
- 规则和配置要可从 Inspector/调试界面观察，遇到失败应给出具体诊断（哪个定义、字段、对象或关卡数据无效）。
- 验证优先选源码检查、配置校验和最小编辑器/PlayMode 验证；遵守项目规则，不默认运行构建、打包、发布或覆盖最终制品的命令。
- 不把未来“可能用到”的抽象提前做进原型；当第三个真实用例出现，或当前改动明显重复/耦合，再决定是否抽象。

## Skill 后续可拆成的模块

若后续要正式写成 Codex Skill，建议保持短入口文件加按需参考资料：

- `SKILL.md`：识别 Unity/引擎、需求定界、检查仓库、最小实现、验证和记录的共同流程。
- `references/architecture.md`：配置/运行时/表现/关卡/调试的边界与何时拆分。
- `references/unity-data.md`：ScriptableObject 字段设计、校验、稳定 ID 和运行时状态规则。
- `references/iteration.md`：AI 每轮的范围、验收、版本控制、测试与制品安全约束。
- 可选 `references/project-template.md`：新项目初始化清单；只在明确新建游戏时加载，避免把模板强加给已有工程。

Skill 的结果应是可迭代的项目规范和可调的数据入口，而不是一次性输出一个更大的 Demo。
